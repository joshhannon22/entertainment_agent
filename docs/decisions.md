# Decisions

One paragraph per real choice, written so it can be said out loud in an interview.

## The agent loop branches on `tool_calls`, and a missing message is terminal (Phase 1, Step 4)

The loop decides "run tools or return an answer" by checking whether the assistant message actually contains `tool_calls`, not by checking `finish_reason`. What the loop needs to know is whether there's work to do, and providers aren't consistent about which `finish_reason` they send. Gemini's OpenAI-compatible endpoint even sends non-standard values like `"content_filter: PROHIBITED_CONTENT"` where the spec says `"content_filter"`. `finish_reason` is still recorded raw in `stop_reason`, so evals and metrics can tell "answered" apart from "truncated", "blocked" or "hit the step cap". A response with no message at all (a safety block) ends the run immediately instead of being retried. The first version retried, and re-sent identical input six times against a filter that was certain to give the same result. Every LLM call is counted toward latency and tokens whatever its outcome, because the requests that fail are the ones a cost dashboard most needs to show.

## `run_agent` returns facts; the caller writes the user-facing message (Phase 1, Step 4)

When the loop ends without an answer (step cap hit, safety block, empty response), `run_agent` leaves `answer=None` and records why in `stop_reason`. It doesn't write a fallback like "Sorry, I couldn't finish". `answer` means "what the model said", and nothing else. The eval script, the CLI and later the HTTP API all consume the same result and need different things from it. The eval has to count a step-cap hit as a failure, the CLI wants a friendly sentence, and an API might return a different status code. A canned string in `answer` would be scored as a real answer and hide the failure rate. Same principle as a service returning an error code rather than a display string: keep the core returning structured data and render it at the edge. A related trap: a turn with neither text nor tool calls first produced `answer=None, stop_reason="stop"`, a "success" with nothing in it. It now keeps a meaningful `finish_reason` (e.g. `length`) or becomes `empty_response`.

## When the API can't answer the question, the schema tells the model how to work around it (Phase 1, Step 5)

The Phase 1 target question is "find me a cheap co-op game", but CheapShark has prices and no genre, tag or player-count data. Three options: add a second data source with tags (more keys and integration work, out of scope for Phase 1), filter in code (impossible, the data isn't there), or **let the model choose candidate titles from its own knowledge and use the tool only for what it's good at, which is real prices**. I chose the third and wrote it into the schema description as an explicit instruction ("Do NOT use it to discover games by co-op… pick specific titles you are confident fit, then call this once per title"). Measured result: with that description the model made parallel lookups of five real co-op games. With a vague description it searched for the literal string "co-op", invented a price cap, and recommended games because "CO-OP" was in their names. The cost is that "this is a co-op game" is now ungrounded model knowledge, so the Step 8 evals have to check it separately from prices. The proper fix is a tagged catalog, in Phase 3 or Phase 4. In a customer setting this is the common case: the system of record doesn't hold the field the user is asking about, and you have to decide out loud which parts of the answer are grounded.
