# Decisions

One paragraph per real choice, written so it can be said out loud in an interview.

## Why hand-write the agent loop before using a framework (Phase 1)

I wrote the ReAct loop myself (call the model, run the tools it asks for, feed results back, repeat until an answer or a step cap) before moving to Google's ADK. It's about 100 lines, and every one of them is something a framework does for you invisibly: keeping the message history (the model is stateless, so that history *is* its memory), matching each tool result to its `tool_call_id`, passing back provider-specific fields like Gemini's `thought_signature` untouched, deciding when to stop, turning tool failures into error messages the model can reason about instead of crashes, and counting tokens, including the hidden thinking tokens that were about half of one early request's bill. Each of those broke at least once while I built it, and each failure taught me what the symptom looks like (a 400 saying `function_response.name cannot be empty` really means "your message order is wrong"). The payoff is debugging. When an ADK agent misbehaves in a customer environment, I know what is happening underneath and can find which layer is wrong instead of treating the framework as a black box. The cost was a few sessions, and the loop stays in the repo as a reference that I'll compare against ADK in Phase 1b. I wouldn't hand-write a loop for a customer. The framework gives you sessions, tracing, evals and deployment targets for free. But I'd want everyone on the team to have written one once.

## The agent loop branches on `tool_calls`, and a missing message is terminal (Phase 1, Step 4)

The loop decides "run tools or return an answer" by checking whether the assistant message actually contains `tool_calls`, not by checking `finish_reason`. What the loop needs to know is whether there's work to do, and providers aren't consistent about which `finish_reason` they send. Gemini's OpenAI-compatible endpoint even sends non-standard values like `"content_filter: PROHIBITED_CONTENT"` where the spec says `"content_filter"`. `finish_reason` is still recorded raw in `stop_reason`, so evals and metrics can tell "answered" apart from "truncated", "blocked" or "hit the step cap". A response with no message at all (a safety block) ends the run immediately instead of being retried. The first version retried, and re-sent identical input six times against a filter that was certain to give the same result. Every LLM call is counted toward latency and tokens whatever its outcome, because the requests that fail are the ones a cost dashboard most needs to show.

## `run_agent` returns facts; the caller writes the user-facing message (Phase 1, Step 4)

When the loop ends without an answer (step cap hit, safety block, empty response), `run_agent` leaves `answer=None` and records why in `stop_reason`. It doesn't write a fallback like "Sorry, I couldn't finish". `answer` means "what the model said", and nothing else. The eval script, the CLI and later the HTTP API all consume the same result and need different things from it. The eval has to count a step-cap hit as a failure, the CLI wants a friendly sentence, and an API might return a different status code. A canned string in `answer` would be scored as a real answer and hide the failure rate. Same principle as a service returning an error code rather than a display string: keep the core returning structured data and render it at the edge. A related trap: a turn with neither text nor tool calls first produced `answer=None, stop_reason="stop"`, a "success" with nothing in it. It now keeps a meaningful `finish_reason` (e.g. `length`) or becomes `empty_response`.

## When the API can't answer the question, the schema tells the model how to work around it (Phase 1, Step 5)

The Phase 1 target question is "find me a cheap co-op game", but CheapShark has prices and no genre, tag or player-count data. Three options: add a second data source with tags (more keys and integration work, out of scope for Phase 1), filter in code (impossible, the data isn't there), or **let the model choose candidate titles from its own knowledge and use the tool only for what it's good at, which is real prices**. I chose the third and wrote it into the schema description as an explicit instruction ("Do NOT use it to discover games by co-op… pick specific titles you are confident fit, then call this once per title"). Measured result: with that description the model made parallel lookups of five real co-op games. With a vague description it searched for the literal string "co-op", invented a price cap, and recommended games because "CO-OP" was in their names. The cost is that "this is a co-op game" is now ungrounded model knowledge, so the Step 8 evals have to check it separately from prices. The proper fix is a tagged catalog, in Phase 3 or Phase 4. In a customer setting this is the common case: the system of record doesn't hold the field the user is asking about, and you have to decide out loud which parts of the answer are grounded.

## Metrics are pure functions over the run record, and prices live in code (Phase 1, Step 6)

The loop records raw facts per LLM call (latency, prompt/completion/total tokens, finish reason) and per tool call (latency). It computes nothing. Cost and throughput are derived afterwards by `metrics.summarize()`, a pure function with no I/O. The same function then serves the CLI today, the eval runner's p50/p95 next, and a Prometheus or OTel exporter in Phase 6, and changing a price never means re-running the agent. Cost counts hidden thinking tokens (`total − prompt − completion`) at the output rate, because that's how Gemini bills and they were half of one early request's tokens. Prices sit in a dict in the code with the source URL and the date checked, not in env vars. They're per-model reference data that should be reviewed like code, and they change on a schedule (3.8 Flash doubles on 2027-01-01). An unknown model reports cost as `n/a` instead of raising, because a metrics bug should never fail a user request. In production this table would come from the billing export (BigQuery) so the dashboard and the invoice agree.

## Where state lives: hand-written loop vs ADK sessions (Phase 1b)

In my Phase 1 loop, all state was one Python list, `messages`, created fresh in each `run_agent()` call and thrown away when it returned. The model is stateless, so that list was its entire memory, and the CLI could never answer a follow-up question. ADK splits the same idea into three things. **Events** are the conversation history: the user message, the model's `function_call`, the tool's `function_response`, the final text, each with its token usage. That is my `messages` list, but it's stored, not discarded. **State** is a separate key-value scratchpad that the agent or tools write to on purpose (`tool_context.state["budget"] = 10`), scoped by prefix: no prefix for this session, `user:` across a user's sessions, `app:` for everyone, `temp:` for the current turn only. A **Session** holds both, and a **SessionService** decides where sessions live: in memory, a local SQLite file (`adk web` wrote `.adk/session.db`), a database, or Vertex AI. When I asked a follow-up without naming the show, the agent remembered it even though the State tab was empty, because memory comes from replaying events, not from state. State is for structured facts you want to read back deliberately ("hates horror", "budget $10") without making the model dig through the transcript. This matters operationally: in Phase 2, with three replicas and in-memory sessions, a follow-up landing on a different pod loses the conversation. Phase 6 fixes that by pointing the SessionService at Postgres, which changes the configuration, not the agent code.

## Hand-written loop vs ADK (Phase 1b)

I built the same three-tool agent twice: a ~100-line ReAct loop on Gemini's OpenAI-compatible endpoint, then on ADK. ADK replaced three things. The JSON schemas became type hints plus docstrings. The loop became ADK's Runner (same shape in the dev UI: `function_call` → `function_response` → text). And the throwaway `messages` list became stored sessions, so follow-up questions work. It also added a dev UI with an event trace, built-in eval metrics (token breakdown including reasoning tokens, model/tool/framework time; framework overhead was 0.02–0.9 s per request), and a path to Cloud Run, GKE or Agent Engine. What it cost: ADK uses the native Gemini API, so changing provider is no longer a base-URL swap. Its defaults need checking (500 LLM calls per run vs my 6; `{}` in a string instruction is state templating). And the hidden behavior I learned in Phase 1 (message order, `thought_signature`, tool-error handling) is now inside the framework, which is exactly why writing the loop first was worth it: when ADK misbehaves I know which layer to look at. For a customer I'd use ADK. I'd keep the hand-written loop as the mental model for debugging it.

## Two eval harnesses, because each catches what the other can't (Phase 1b)

My Phase 1 script checks **properties I can state in code**: the expected tools were called, no tool argument contains "co-op" (the vague-schema failure), the minimum and maximum tool calls, required words in the answer, every $price in the answer appears in a tool result, and it runs each case N times for a pass rate and p50/p95. `adk eval` checks **trajectory** (configured `ANY_ORDER` + `ignore_args`, because the default `EXACT` compares arguments and fails any question where the agent picks its own titles) and **groundedness with an LLM judge** (`hallucinations_v1`: split the answer into sentences, check each one against the tool output). It also reports cost and latency breakdowns for free. On the first run ADK scored 8/10 and caught something my script never could. Both failures were judge scores of 0.64 on recommendation questions, because the "vibe"/premise sentences come from the model's own knowledge, not the tools (Open Library returns no synopsis, and CheapShark has no genre). That's the ungrounded "fits the request" part I noted in Step 5, now measured. ADK couldn't express several of my checks: "zero tool calls" (an empty expected list matches anything under `ANY_ORDER`), argument contents, and N runs from the CLI. It also passed `tv_not_found` even though the agent wasted calls searching books and games for "Zorblax". So I keep both. The script is the cheap deterministic gate for CI, and the judge is the slower, costlier groundedness check. The judge has a cost too: about two extra LLM calls per case, and it's a model grading a model, so its scores need spot-checking just like the agent's.

Follow-up: tightening the instruction (describe items only with tool data, plus one short "why I picked it" phrase) moved `book_recommend` from 0.64 to 1.0 and `three_tools` from 0.86 to 1.0. `game_coop_strategy` only reached 0.77, because the leftover unsupported sentences are the "it's a co-op game" phrases, which no tool can confirm. I kept the 0.8 threshold rather than lowering it to pass. That failure is accurate, and the fix is giving the agent genre data (Phase 4), not changing the test.


## Our own FastAPI wrapper instead of ADK's `get_fast_api_app` (Phase 2)

ADK ships a ready-made FastAPI app (`adk api_server` / `get_fast_api_app`), but it's built for the dev UI: session-shaped routes plus eval, trace and builder endpoints you wouldn't expose in a regulated environment. We wrote a ~100-line wrapper around `Runner` with exactly two routes: `POST /chat` (message plus optional `session_id`, returns the answer with tool calls, token counts, latency and the serving pod) and `GET /healthz`, which never calls the LLM so a Gemini outage can't become a restart storm. The trade-off is that we own the request/response contract and miss ADK's SSE streaming for now. Owning the contract is what a customer's platform team wants anyway: a small, documented surface that the evals, CI and later a UI all call the same way. An unknown `session_id` returns 404 rather than silently starting a new session, so the per-pod state problem shows up as an error instead of a confused agent.
